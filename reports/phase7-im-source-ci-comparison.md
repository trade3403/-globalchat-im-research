### 消息链路中的差异

- **悟空 IM**：入口将发送命令交给频道追加路由；提交后才生成供收件人规划使用的消息封装。在线投递又把接受、可重试和丢弃分别记录，因此发送端确认和接收端投递可分开观察。
- **JuggleIM**：WebSocket 帧进入连接管理器，内部调用保留 `app_key`。私聊路径在分发前应用黑名单、好友规则和拦截器，再记录发送箱和历史。上游压测分别记录服务端 ACK 和收件端回调，回调统计无法直接推导未收到的消息数。
- **OpenIM**：服务端 REST 入口把消息交给消息 RPC，接收者可按会话序号查询历史。客户端 SDK 的 `MsgSyncer` 维护本地序号，在建立连接或处理推送时比较本地与目标序号，并拉取缺失区间。本次 REST 测试覆盖服务端序号拉取，SDK 重连和本地库仍待单独实测。

## 三家优势总结与可学习之处

本节只归纳三个竞品的源码结构、产品能力和本轮 CI 观察，不对应任何自有产品代码或改造任务。

| 项目 | 核心优势 | 源码与测试依据 | 可学习的设计经验 |
|---|---|---|---|
| 悟空 IM | 消息引擎、频道模型和集群投递 | 频道追加、在线投递有分开的契约与运行时；三节点跨节点消息用例通过。账号、好友和业务权限由上层应用负责。 | 明确区分消息提交与后续投递；把节点路由、投递结果和可重试/丢弃状态作为清楚的边界；用跨节点用例验证集群语义。 |
| JuggleIM | IM 核心外的业务服务与运营管理 | 多租户 `app_key` 沿 API、内部调用和消息链路传递；独立业务服务提供账号、好友和群功能，控制台管理应用、消息和集成。本轮单机 Compose 私聊与群聊场景通过，但临时修正了初始化 SQL。 | 让租户身份贯穿所有数据访问；把消息传输核心与社交业务、运营控制台分层；为运营动作提供明确的权限和管理入口。 |
| OpenIM | 服务端 API 与多端 SDK 配套、序号同步 | 服务端按会话序号拉取历史；SDK `MsgSyncer` 维护本地序号，并在连接或推送事件后补拉缺失消息。本轮源码构建和 REST 私聊历史闭环通过。 | 客户端同步器与服务端序号协议协同设计；使用持久化游标做断线恢复；多端 SDK 共享同步逻辑和事件接口。 |

### 横向观察

1. **三家各自选择了不同产品边界。** 悟空 IM 更集中在消息引擎，JuggleIM 同时提供业务服务与运营台，OpenIM 着重服务端 API 和跨平台客户端 SDK。
2. **可靠性必须拆成不同阶段验证。** 服务端接受消息、消息跨节点路由、收件设备确认、离线历史补齐是不同环节，单一“发送成功”不足以覆盖完整收发。
3. **功能丰富度与部署复杂度相关。** 内置组件可以减少外部拼装，但多服务、多数据库和多平台 SDK 会提高升级、配置和排障要求。
4. **源码可读性来自职责边界与可观察结果。** 追加、投递、租户上下文、同步游标等核心机制都应能从代码入口追到状态变化，并由自动化场景验证。

### 产品层谁做得更完整

如果“产品层”指用户可见的社交业务，加上运营人员能直接使用的管理后台，**JuggleIM 配套的 JuggleChat 与 imserver-console 覆盖最完整**。它不止提供消息收发核心，还把注册登录、个人资料、好友申请与黑名单、群邀请与成员角色、禁言和公告等业务能力放进独立业务服务；控制台另有应用管理、用户封禁、会话与历史消息、敏感词、消息拦截器、推送/存储/RTC 配置和运行统计。这些模块组合起来，更接近可供团队搭建一款聊天产品的业务层和运营工具。

**OpenIM 的产品优势更偏客户端接入与多端一致性。** Server 提供用户、好友、群组、消息、会话相关 API 和 WebHook；SDK 核心覆盖本地存储、连接管理、回调、好友/群组/会话和消息同步，便于多个客户端共享接入逻辑。它的交付重点是开发者集成底座，完整社交 App 的用户体验仍需业务应用和客户端完成。

**悟空 IM 更像可嵌入产品的消息基础设施。** 内置 Manager 面向集群、连接、频道、消息、诊断和备份等运维操作，示例应用展示聊天和客服场景；账号、好友关系、业务权限和完整客户端体验留给上层应用构建。它的长处是统一消息模型和集群消息能力，不能按完整社交产品后台来衡量。

| 产品层判断 | 结论 |
|---|---|
| 完整社交业务与运营后台 | JuggleChat + JuggleIM Console 覆盖面最完整 |
| 多端 SDK 与消息同步接入 | OpenIM SDK 更突出 |
| 消息底座与集群运维 | 悟空 IM 更突出 |
| 本轮实际验证范围 | JuggleIM 单机私聊/群聊场景；OpenIM 源码构建与 REST 私聊历史；悟空 IM 三节点跨服消息测试。各 CI 未逐项验证所有菜单或所有客户端功能 |

此判断基于对应仓库的公开源码、README 和控制台功能说明。产品模块存在不等于每项都经生产环境验证；JuggleIM 本轮验证的私聊/群聊范围有限，且需在 Runner 临时修正初始化 SQL。完整模块列表见 [JuggleChat](https://github.com/juggleim/jugglechat-server) 和 [JuggleIM Console](https://github.com/juggleim/imserver-console)。

## 后续产品特征测定矩阵

以下测试用于在三家之间形成可复现的产品能力基线，当前尚未全部执行。执行时固定每家源码提交、依赖镜像版本、Runner 型号、配置、测试账号和数据集；每项同时记录源码入口、实际操作步骤、结果、日志及限制。菜单或 API 存在只算“代码/入口已发现”，通过运行测试才算“本次已验证”。

| 特征组 | 统一测试场景 | 记录指标与证据 | 通过标准 |
|---|---|---|---|
| 账号与多租户 | 注册/创建用户、登录、退出、禁用用户；若系统支持租户则创建两个租户并尝试跨租户访问 | 操作 API、身份/租户字段、HTTP/RPC 结果、审计日志 | 合法操作成功；禁用身份无法继续访问；租户 A 不能读写租户 B 的用户、会话或消息 |
| 好友与群组 | 双用户好友申请/同意/拒绝/拉黑；创建群、邀请成员、变更角色、禁言、退出/解散 | 状态迁移、成员列表、操作者权限、重复请求行为 | 状态符合请求；无权限角色不能执行管理操作；重复请求不产生重复关系或成员 |
| 私聊与群聊 | 固定两个客户端、每场景 100 条带唯一 ID 消息；检查发送 ACK、收件回调、历史记录及离线补收 | 发送数、ACK 数、目标设备收到数、缺失/重复/乱序数、P50/P95/P99 | 在线与离线历史集合和预期消息集合一致；每条消息按 ID 核对，报告顺序语义与异常 |
| 撤回、删除与已读 | 发送、接收、标记已读、撤回、删除，并分别从发件人、收件人、管理端重新查询 | 操作授权、状态和序号变化、各角色查询可见性 | 权限边界符合定义；重复操作幂等；客户端与服务端状态无矛盾 |
| 消息搜索与管理 | 用唯一文本/用户/群 ID 检索历史；管理员按角色执行检索、撤回或封禁 | 命中率、分页完整性、过滤条件、耗时、审计记录 | 测试集合无漏项或跨租户泄漏；所有管理变更均有操作者和时间记录 |

| 管理后台与可运维性 | 以管理员/运营/只读角色执行用户检索、群管理、消息处置、配置变更；触发服务重启 | 菜单/API 覆盖、RBAC 结果、操作审计、健康状态、恢复时间 | 角色权限遵循矩阵；变更可追踪；重启后数据与服务状态满足定义 |

### 对比和报告口径

- 每项用“未检查、源码可见、测试未通过、测试通过、需人工/付费环境”五种状态之一。无证据时不从菜单或宣传文案推断通过。
- 公共测试集使用合成账号、合成内容和唯一消息 ID。所有系统记录源码 SHA、镜像 digest、配置摘要、Runner CPU/内存、系统版本和 UTC 时间。
- 功能正确性与性能分开报告。正确性先验收；性能测试另固定拓扑、客户端数、消息大小、发送速率与持续时间，报告 ACK/接收延迟分位数、吞吐、资源使用和错误率。
- 控制台功能如果没有可公开运行的控制台源码、API 或测试账号，状态记为“需人工/付费环境”，不当作自动化 CI 已覆盖。
- 当前 Phase 7 只验证了悟空 IM 三节点消息用例、JuggleIM 本地私聊/群聊场景，以及 OpenIM REST 私聊历史读取。其余矩阵项均待后续测试。
